# Automation domain (scraping + apply assistant + AI provider)

Last updated: 2026-09-06 (task #16: backend-owned active AI provider store)

Merged knowledge for `scraping-applier-expert` and `ai-provider-expert`. Source is authoritative for board/provider counts.

## Scraping (`scraping/`)

- **Registry** — `scraping/boards/mod.rs`: `SCRAPERS` registry. `Scraper` trait (`Send + Sync` bounds) and `ScraperMode` live in `scraping/types/mod.rs`. Adding a board = implement `Scraper` + register; never special-case outside the registry. Board count lives in the registry — don't copy it.
- **Engine & multi-board** — `scraping/engine/mod.rs`: public entry point `scrape_boards` orchestrates multi-board scraping with concurrency limits (server-side defense against DoS) and auth-aware short-circuiting. Returns structured summaries per board (count, error, skip reason). See `scraping/engine/mod.rs` for concurrency model, cancellation handling, and partial-success semantics.
- **Rate limiting & retry** — `scraping/rate_limiter/` + `scraping/http/`: per-host static registry (`HOST_LIMITERS`) in `scraping/rate_limiter/` with rate limits per board. On HTTP request: wait-for-slot before attempt, record request after success. 429/503 responses parse `Retry-After` (integer seconds) or backoff exponentially with jitter; bounded retries (see `scraping/http/`) prevent network loops.
- **Transport** — HTTP via `scraping/http/` (pooled rustls client). Chromium ([chromiumoxide][chromiumoxide]) used exclusively by `scraping/board_login/` for manual login + encrypted cookie import (reads Chromium's v10/v11 stores, decrypts, writes artifacts via `import_cookies`; see `commands/boards.rs: boards_import_cookies`). LinkedIn-specific flow: `scraping/linkedin/` (HTTP clients using LinkedIn's rate-limit rules).
- **Aggregator board & paid providers** — `scraping/boards/aggregator/`: one `Scraper` in the registry (`id = "aggregator"`) backed by an ordered `JobProvider` list: `AdzunaProvider` (primary) → `JSearchProvider` (fallback) → `JoobleProvider` (third-tier, BYO-key) → `ApifyLinkedInProvider` (additive, opt-in, paid). `search_with_providers` runs the primary chain then merges LinkedIn results additively with URL-dedup. `ApifyLinkedInProvider` runs only when BOTH `apify_linkedin_enabled` toggle AND a keychain token are present; it enforces platform-level spend caps (`maxItems`, `maxTotalChargeUsd` query params), `retries: 0`, and a `tokio::select!` cancellation guard. Provider details (struct defs, validation) in `scraping/boards/aggregator/providers.rs`. See [ADR-028](decision-records/adr-028-additive-aggregator-merge-paid-provider-cost-controls.md).
- **Context** — `ScrapeContext` carries a **cancellation token** + progress/item callbacks. Honoring cancellation, bounded retries/backoff, and per-board rate limits are reliability requirements (ignoring the token or unbounded retries on a network loop = HIGH).
- **Selector resilience** — core boards need fallback selectors; a brittle single-selector parse on a core board is HIGH (it breaks on the next site redesign).
- **Full-description resolve on detail-pane open** — for aggregator sources with short snippets (<700 chars), the detail pane auto-fetches on open by following the redirect chain (IP-guarded, per-hop) and re-dispatching named-board handlers on the final URL. This yields full board-API text when the redirect resolves to a supported ATS; falls back to generic HTML or returns Ok(None) on error. The pane keeps the snippet floor if resolved text is not meaningfully longer (guards against 429/generic degrading the display).
  - **Re-score path:** If resolved text is meaningfully longer than the snippet, the pane calls `scrape_update_description(id, text)` to mutate the `PostingsCache` entry in-place. The match score is re-computed on-demand via `MatchScoresProvider`'s reactive `requested` set + `useJobMatchScore` (per-job scoring, enabled only when the user has opened the job). Per-job cache key (`['match', resumeId, jobId]`) means repeated opens within 10 minutes are free — no re-embed. Unopened aggregator jobs retain cached snippet-based scores (efficient for large batches; convergent per opened job).

## Apply assistant (no auto-apply engine)

- **Decision (2026-06, PR #7 of the UX backlog):** the browser-automation apply engine (`applying/` — board appliers, `captcha_handler`, `form_filler`, the `APPLIERS` registry — plus `commands/apply`, `apply_helpers/`, and the apply IPC contract) was **removed**. The app is an **apply assistant**, not an auto-applier: selector drift, captcha, and per-board form logic made an auto-submit engine too costly to maintain, and it was never user-facing ("Coming Soon"). `chromiumoxide` stays — scraping uses it.
- **What the assistant does** — from a found or scraped job the user tailors a résumé + cover letter (`renderer/features/documents/components/TailorFlow/`, `renderer/store/generation-store/`), gets résumé-grounded application answers, opens the posting in the browser, and submits it themselves. Autopilot (`autopilot/`, `autopilot_scheduler`) **finds → ranks → notifies**; it never submits. Found-jobs PostingRow "Tailor" seeds the AI Generate workspace for any board.
- **Autopilot board picker** — dynamically driven by the board catalog (`useBoardsCatalog()`), so new boards appear automatically without UI changes. The wizard board-select component (`StepTarget`) filters catalog entries by `listed` flag; includes the aggregator board.
- **Autopilot scheduling** — **clock-anchored** (PR #266; was interval-based). `autopilot_scheduler.rs` computes the most-recent scheduled occurrence in local time (`chrono::Local`) via `last_occurrence_ms` / `is_due`; on launch it catches up to any missed run (single catch-up, no double-fire). Frequency modes: `daily` = HH:MM; `twice_daily` = HH:MM + 12 h; `hourly` = :MM; `manual` = no scheduling. Fields `scheduleHour` (0–23) and `scheduleMinute` (0–59) on the autopilot model — Zod-validated client-side, range-guarded in the store. Legacy records default to 09:00.
- **Post-discovery LinkedIn description enrichment (issue #1114, LinkedIn-only slice)** — LinkedIn search results carry no description (`linkedin::api_client`'s comment on that field points here); a scheduled run's `autopilot_run` spawns `commands::autopilot::linkedin_enrich::enrich_linkedin_descriptions` (L3 — Tauri/`AppHandle`-touching orchestration, fire-and-forget via `tauri::async_runtime::spawn`) right after `record_run`, so it can never delay the run's own completion/notification. The pure selection/decision logic it calls into stays one layer down in `autopilot_helpers::linkedin_enrich` (L2), per `docs/architecture-rules.md` R2/R7. It re-fetches each still-blank LinkedIn found-job through the SAME single-URL resolver (`scraping::scrape_url::resolve`) the manual "re-check" and extension-import paths use, paced through `linkedin::rate_limiter::linkedin_rate_limiter()`, and writes any real description back via `commands::scrape::scrape_update_description` (the #1109 write-back mechanism) — never mutating anything else about the job. Selection is pure (`select_linkedin_enrichment_targets`, unit-tested): blank description + `board == "linkedin"`, not `is_new` (so a prior failed attempt retries), capped at `LINKEDIN_ENRICH_MAX` per run. A per-URL failure is logged and skipped, never surfaced as a run error. The other six description-blank boards named on `no_jd_text` (TheMuse, Comeet, Breezy, BambooHR, Pinpoint, Rippling) have no equivalent single-URL detail resolver yet — out of scope here.
- **Autopilot RUN filters** — a run applies three filters (date window, must-include keywords, min-match-score) that manual search does not; defaults realigned to manual parity via `AutopilotFilterSchema` Zod schema (packages/shared/src/schemas/index.ts) → generated Rust contract. Wizard `buildDefaults()` mirrors schema defaults. One-shot, marker-file-gated migration on first `autopilot_scheduler::start` calls `relax_legacy_filters_once` → `relax_legacy_filters` (pure logic) to loosen legacy saved autopilots per sentinel rules. Diagnostics: `scrape_diagnostics` surfaces per-board skip/error reasons into the autopilot run step log; `scrape_done` reports raw vs post-keyword-filter job counts.
- **"Applied" tracking** — found-job enrichment: a found job is marked "applied" when a saved generation's `jobUrl` matches it (`commands/autopilot.rs: enrich_applied`). Separate paths now also auto-set application status: extension submit-watch form-tracking (opt-in, #687) and email-confirmation watching (#23, see section below). Each autopilot keeps an optional **base cover letter** (`coverLetter`) the assistant tailors per job.
- **Assistant-notes provider resolution (task #16, behavior change)** — the per-record `assistant_provider/model/base_url` snapshot is gone; a scheduled/headless run now resolves the AI-reasoned-note provider via `Completer::from_active` — the **currently-active** provider at run time, not the one pinned when the schedule was created (owner-accepted semantics change; see [ADR-0012](decision-records/0012-ai-provider-base-url-provenance.md)). Missing/unknown/invalid provider → notes are skipped gracefully; the discovery run still completes. The renderer wizard's `assistantProvider`/`assistantModel`/`assistantBaseUrl` fields are now vestigial (always sent `undefined`).

### Run status & honesty (PR B, 2026-07-10; diagnostics surface PR C, 2026-07-10)

Autopilot runs now persist per-board summaries and derive honest status:

- **`RunStatus` enum** — `Completed`, `CompletedWithErrors` (some boards failed, run finished), `Failed` (zero boards succeeded), `Interrupted` (user cancelled). Source: `apps/desktop/src-tauri/src/autopilot/mod.rs`.
- **Per-board summaries** — `Autopilot.last_run_summaries: Vec<BoardScrapeSummary>` (persisted, defaulted empty for old records). Each summary carries `count`, `error`, `skipped`, and `truncated` signals. Source: `apps/desktop/src-tauri/src/autopilot/mod.rs`.
- **Derivation** — `derive_run_status(&[BoardScrapeSummary]) -> RunStatus` (pure fn). Rules: empty → `Completed`; all boards errored/skipped → `Failed`; any error/truncated present → `CompletedWithErrors`; else → `Completed`.
- **Store load tolerance** — `AutopilotStore::load()` parses as `Vec<serde_json::Value>` first, deserializes each record individually, drops+logs only the failures (e.g. an unrecognized `runStatus` from a newer build during downgrade). Prior behavior (ONE bad record wiped the entire file on next save) is fixed. Source: `apps/desktop/src-tauri/src/autopilot/mod.rs: load()`.
- **IPC contract** — `AutopilotRunStatus` + `Autopilot.runStatus` + `Autopilot.lastRunSummaries`. Source: `packages/shared/src/ipc/contracts/autopilot.ts`, `packages/shared/src/types/index.ts`.
- **Renderer — render surface (PR C)** — `BoardSummaryChips` component renders sanitized per-board diagnostics (count, error reason, skip/truncated state) as a persistent chip strip. Reused by three surfaces: (1) Jobs page header (pinned, survives form auto-close); (2) Jobs empty state (sole owner of zero-results explanation); (3) Autopilot card (persisted `lastRunSummaries`, survives step-log unmount). Needs-configuration variant (all-skipped, no errors) renders neutral badge vs red failed state. Source: `apps/desktop/src/renderer/components/scrape/BoardSummaryChips.tsx` (+ unit tests). IPC-wired to `useAutopilotRun.ts` (status branching) and `AutopilotCard` (runs finished badge). `useAutopilotRun.ts` branches on `status === 'failed'` (sets error state, reuses red banner). Sources: `apps/desktop/src/renderer/features/autopilot/hooks/useAutopilotRun.ts`, `apps/desktop/src/renderer/features/autopilot/components/AutopilotCard/`, `apps/desktop/src/renderer/features/jobs/components/JobsPage/index.tsx`, `apps/desktop/src/renderer/features/jobs/components/JobsResults/index.tsx`.

### Retry design & concurrent-run guard (PR H, 2026-07-11)

Bounded retry + run guard + provisional-score honesty:

- **Bounded retry** — when a run fails or is interrupted, the scheduler retries ONCE after a short backoff (`RETRY_BACKOFF = 12 min`). The retry is in-process (not persisted); no new schema field. A retry pending at app close is dropped (next scheduled occurrence still runs on next startup). Design: `outcome_failed` checks payload for `error` or `status=="failed"` (never for `completed`/`completedWithErrors`/`cancelled`/`skipped`); `run_with_single_retry` runs → sleeps → runs once more, with the retry's outcome deliberately NOT re-checked (structurally impossible to storm). **Interrupted arm** (from crash recovery): `schedule_interrupted_retries` now re-validates via `still_needs_recovery(ap, baseline_last_run_at)` immediately before firing — catches the race where a regular `tick` already re-stamped `last_run_at` while the recovery task slept. Source: `apps/desktop/src-tauri/src/autopilot_scheduler.rs`.
- **Concurrent-run guard** — process-global `RUNS_IN_FLIGHT: LazyLock<Mutex<HashSet<String>>>` + RAII `RunGuard`. If an id is already in flight, `autopilot_run` early-returns `{ skipped: "already-running" }` (honest signal to the renderer). Guard releases on every exit path (early return + panic unwind). Renderer's `useAutopilotRun.handleRun` treats the response as benign `'done'` or surfaces it as a distinct error message (`t('autopilot.wizard.alreadyRunning')`). Source: `apps/desktop/src-tauri/src/commands/autopilot.rs`.
- **Provisional-score flag** — aggregator sources (Adzuna snippet text) AND any posting whose scoring blob had no usable description/requirements text (issue #1105) are flagged `scoreProvisional: true`; see `no_jd_text`'s own doc comment in `build_found_job` for the exact predicate. Renderer styles provisional scores as muted + subtle band + sr-only hint (see the `autopilot.provisionalScoreHint` translation key for current wording). Conservative: JSearch (aggregator fallback) is also flagged provisional even though it returns full text (under-stating confidence is the safe direction). Source: `FoundJob.score_provisional: bool` (Rust), `AutopilotFoundJob.scoreProvisional?: boolean` (TS), `build_found_job` in `apps/desktop/src-tauri/src/commands/autopilot.rs`.
- **Field-level merge honesty** — when a job resurfaces across multiple sources, `merge_found_jobs` now carries `score_provisional` alongside `score` in the field-level-upgrade path. A snippet score resurfaced by a full-text board flips the flag to `false` (now authoritative); full-text resurfaced by a snippet flips to `true` (now provisional). Bidirectional regression test asserts both directions work and the worse case (snippet score masquerading as authoritative) is explicitly rejected. Source: `apps/desktop/src-tauri/src/autopilot/mod.rs`.

- **Security** — never log credentials/cookies; board session handling for **scraping** is co-reviewed by `tauri-security-reviewer`.

### Best Matches — cross-autopilot fuzzy ranking

A deduplicated ranked surface across all non-archived autopilots' found jobs (paused autopilots
contribute; archived do not). Computed at query time by clustering the union of all records' found
jobs, ranking via [ADR-020](decision-records/adr-020-unified-autopilot-scoring-kernel.md)'s
two-block rule, and capping the wire payload at `BEST_MATCHES_CAP`
(`apps/desktop/src-tauri/src/commands/autopilot/best_matches.rs`). Dismissed jobs are excluded. See [ADR-036](decision-records/adr-036-cross-autopilot-best-matches.md).

- **IPC contract** — `AutopilotContract.bestMatches()` → `AutopilotBestMatchesResult` (matches, total count, contributing autopilot count). Source: `packages/shared/src/ipc/contracts/autopilot.ts`.
- **Rust command** — `commands/autopilot/best_matches.rs`: pure `compute_best_matches` + async IPC wrapper. Dedupes the union on `canonical_job_key`, clusters via `scraping::cluster::assign_clusters`, selects best member per cluster via the two-block rule, filters by qualification (best member >= its own kernel's high cut), and sorts Combined-first then Keyword-first each by score desc + key asc.
- **Renderer surfaces** — `/best-matches` route with sort options (score desc, newest first, salary), empty states (no autopilot run yet vs. run completed, nothing qualified), and a truncation notice. `BestMatchRow` component reused by the Best Matches page and the `/autopilot` route's preview strip. Dismiss action via `useBestMatchActions` persists to `InteractionStore` as `interaction_type: 'dismissed'`, matching per-member on `canonical_job_key` and rolling back optimistically if the persist fails.
- **Query key** — `keys.autopilot.bestMatches` (a child prefix of `keys.autopilot.all`, so fresh autopilot runs invalidate best-matches queries via prefix match).

## Email confirmation watching (task #23, auto-track Layer C)

- **Purpose** — complement to extension submit-watch: listen for confirmation emails on application submission and auto-set application status to "applied" + capture metadata (job title, company, salary, start date) from parsed email body. Polling-based watcher for IMAP-enabled mailboxes (Gmail, Outlook, auto-config for known providers).
- **Components** — `apps/desktop/src-tauri/src/email_watch/`: `mod.rs` (EmailWatchStore with account/status persistence), `imap_client.rs` (IMAP connection + TLS), `matcher.rs` (regex for confirmation emails), `parser.rs` (extract metadata from MIME), `poller.rs` (background poll loop). Scheduler: `email_watch_scheduler.rs` (startup + tick-based intervals). IPC: `commands/email_watch.rs` (verify, start, stop). See [ADR-0013](decision-records/0013-email-confirmation-watching.md).
- **Credential handling** — passwords are **never persisted**; IMAP credentials are validated on-demand via `verify` (request → check connectivity → dismiss without storing). Active watchers store only the email address + IMAP host (provider auto-detected); password re-enters on every poll cycle (user's system keychain, e.g., macOS Keychain, Windows Credential Manager, or Linux Secret Service via a future integration).
- **Lifecycle** — user opts in via settings (EmailWatchSettings component), verifies account access, starts watch. Poller runs on a schedule (default 5 min), fetches new emails matching the confirmation regex, parses metadata into an embedded EmailMetadata struct, calls `commands/applications: set_status(...auto:true)`, and clears the "unread" flag. On error (auth lapsed, network), poll backs off and retries; critical errors pause the watch (user must reverify).
- **Metadata extraction** — parser handles common confirmation formats (plain text, HTML MIME) to extract job title, company name, salary/compensation, and target start date. Structured as `EmailMetadata { title?, company?, salary?, startDate? }`; incomplete extractions are soft-failed (partial data accepted, missing fields skipped). Extraction is conservative — favors false negatives over noisy extraction.
